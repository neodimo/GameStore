## 2026-08-24 — find the MiSTer by name, and stop the scan taking a minute

- **What was done:** Omid could not reliably connect to his MiSTer and suspected its address changes more than he realised. He is right, and the app made it worse by treating a DHCP lease as the device's identity. Three changes. **(1) The device is named, not addressed.** Settings now leads with a device name defaulting to `MiSTer.local` — a MiSTer runs avahi and answers to its own hostname — and the address became a cache the app refreshes itself. `electron/mdns.ts` is a one-shot multicast resolver written for this, because the OS resolver cannot be relied on: Windows and macOS answer `.local` natively but a Linux host needs `nss-mdns` wired into `nsswitch.conf`. It sets the unicast-response bit and binds an ephemeral port, so it never fights a system avahi-daemon for 5353. **(2) A stale address triggers a search, not an error.** `locateDevice` tries the saved address, then every candidate name in one multicast round trip, then the sweep — and adopts a rediscovered candidate only if it presents the SSH host key recorded on first connection. **(3) The scan got 8× faster**, which was an accident of investigating the first two. **Evidence:** verified against the live network, not only in tests. `resolveMdns` resolved `bazzite.local` → 192.168.4.171 by real multicast query. Host-key identity was exercised against a real SSH server at 192.168.4.96: the key `FqNJOsj3FLUoMQxgn+cqGoXvVfENmVK4QFoSCMKl2lU=` was captured during the handshake, a matching key reached authentication, and a deliberately wrong key was refused with `Host denied (verification failed)` **before** authentication — so a wrong device never sees the password.
- **Artifacts:** Branch `reliable-mister-discovery`, version 0.16.0. Added `electron/mdns.ts`, `electron/mdns.test.ts`, `electron/networkDiscovery.test.ts`. Modified `electron/networkDiscovery.ts`, `electron/main.ts`, `electron/preload.ts`, `src/App.tsx`, `src/style.css`, `src/vite-env.d.ts`, `CONTEXT.md`, this log. No new dependency: the mDNS resolver is about 140 lines of `node:dgram`.
- **State:** Released as **v0.16.0** at `https://github.com/neodimo/GameStore/releases/tag/v0.16.0` (public, non-draft, non-prerelease). PR #39 verification passed in 1m16s, merged at `6ed3c7c`, and release run `32810445390` succeeded. Verified assets: Windows installer 92,828,000 bytes, blockmap 96,781 bytes, AppImage 123,510,102 bytes, Debian package 84,432,664 bytes, plus both updater manifests. 180 tests pass (13 new), TypeScript clean, both production builds succeed, media-light guard passes at 2.59 MiB of 5.00 MiB. **Measured, before and after:** a full "device is gone, look everywhere, fail cleanly" cycle went 103s → 13s, and `discoverFpgaDevices` went 58.5s → 7.7s. **Unverified:** no MiSTer was reachable during this work, so the success path — adopt a moved device, save its address, tell the renderer — is proven by unit tests against real sockets and by the host-key probe above, not by an actual MiSTer changing address.
- **Next owner + concrete artifact:** Omid installs v0.16.0, opens Settings, and leaves **Device name** as `MiSTer.local`. **Diagnostic he should know:** during this work his network showed no mDNS answer for any MiSTer name, while 192.168.4.96 accepted root password authentication and 192.168.4.54 did not — so .96 is very likely the MiSTer and it is **not** advertising `MiSTer.local`. If avahi is not running on it, `systemctl enable --now avahi-daemon` on the MiSTer makes the name work; without that the app still self-heals, just via the slower scan path.
- **Failure mode:** Two, and the second is the instructive one. First: identity was never modelled at all — the app stored a lease and called it a device, so every address change looked like a broken connection. Second: **I guessed at the slow path twice and was wrong both times.** After the fix the cycle was still 73s; I blamed SSH handshake timeouts and shortened them, then blamed serial vetting and parallelised it — 72s. Only measuring each stage showed the entire cost was `dns.reverse()` inside the sweep loop, 31 seconds for four hosts, because an address with no PTR record waits out the resolver's full retry budget. A cosmetic label was setting the pace for the whole operation. Two rules fell out: time the stages before optimising any of them, and put a budget on every lookup that is worth having but never worth waiting for.
