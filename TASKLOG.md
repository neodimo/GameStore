New shared `runOnPcTarget()` in `main.ts` opens the SSH connection (or runs locally) once per action and is now the one place that branch lives, since core management and the deploy pipeline will need the identical connect-or-run-locally shape next.

## 2026-08-30 — PC target identity, OS detection, and execution (real implementation, first slice)

- **What was done:** DiMo said to start building the remote-execution question raised against the v009 mockup: a PC deploy target needs to be identified as Windows or Linux and connected to before anything can be installed or written to it. Built exactly that foundation — not RetroArch install or `shortcuts.vdf` writing yet, both of which depend on knowing the target's OS first. New `electron/pcTarget.ts`: `localOs()` maps `process.platform` directly (the local case needs no network at all, per DiMo's "should work as local... easily"); `detectOsFromProbe()` identifies a connected shell by what it actually does rather than a banner — `uname -s` is the universal Unix answer, and a Windows OpenSSH server's default shell (`cmd.exe`, what Win32-OpenSSH spawns unless reconfigured) simply doesn't recognize that command, so a `uname` failure is itself the signal to try `cmd /c ver`, which only `cmd.exe` understands; `execLocal`/`execRemote` are the two execution edges (child_process vs. an SSH exec channel), and `connectPcSsh` opens the SSH connection using the exact same host-key-pinning identity contract already proven for MiSTer (`hostVerifier` captures the SHA-256 key and, when a previous key is on file, rejects a mismatch before authentication) — a remote PC target is trusted the same way a MiSTer is, not adopted on address alone.
- **Wiring:** `ProviderSettings` gained a `pcTarget` field (kind local/remote, name, host, port, username, encrypted password, pinned host key, last-detected OS) alongside the existing `fpga` field, with the same password-encryption-at-rest treatment. Three IPC handlers (`pc-target-get/set/test`) mirror the `fpga-settings-*` shape; `pc-target-test` is the one that actually does something: local just calls `localOs(process.platform)` and returns instantly, remote reuses `isReachable()` (the same 450ms TCP probe that keeps a stale MiSTer address from hanging SSH for a minute) before ever handshaking, then connects, runs the two-probe OS detection over the live channel, records the host key, and disconnects. New Settings tab "PC / Steam": target picker (this machine / a remote PC), name/address/port/username/password fields that only appear for a remote target, last-detected-OS readout, and a connect/detect button.
- **Evidence:** `electron/pcTarget.test.ts`, 7 tests — Linux and macOS identified from `uname -s`, the Windows fallback path (uname fails → `cmd /c ver` succeeds), a `uname` that rejects entirely (dropped SSH channel) still falling through to the Windows probe, a genuinely unrecognized shell throwing rather than guessing, and a `localOs` platform-mapping check. Full suite: `npm run lint`, `npm test` (**16 files / 232 tests**), `npm run build`. ## 2026-08-24 — find the MiSTer by name, and stop the scan taking a minute

- **What was done:** Omid could not reliably connect to his MiSTer and suspected its address changes more than he realised. He is right, and the app made it worse by treating a DHCP lease as the device's identity. Three changes. **(1) The device is named, not addressed.** Settings now leads with a device name defaulting to `MiSTer.local` — a MiSTer runs avahi and answers to its own hostname — and the address became a cache the app refreshes itself. `electron/mdns.ts` is a one-shot multicast resolver written for this, because the OS resolver cannot be relied on: Windows and macOS answer `.local` natively but a Linux host needs `nss-mdns` wired into `nsswitch.conf`. It sets the unicast-response bit and binds an ephemeral port, so it never fights a system avahi-daemon for 5353. **(2) A stale address triggers a search, not an error.** `locateDevice` tries the saved address, then every candidate name in one multicast round trip, then the sweep — and adopts a rediscovered candidate only if it presents the SSH host key recorded on first connection. **(3) The scan got 8× faster**, which was an accident of investigating the first two. **Evidence:** verified against the live network, not only in tests. `resolveMdns` resolved `bazzite.local` → 192.168.4.171 by real multicast query. Host-key identity was exercised against a real SSH server at 192.168.4.96: the key `FqNJOsj3FLUoMQxgn+cqGoXvVfENmVK4QFoSCMKl2lU=` was captured during the handshake, a matching key reached authentication, and a deliberately wrong key was refused with `Host denied (verification failed)` **before** authentication — so a wrong device never sees the password.
- **Artifacts:** Branch `reliable-mister-discovery`, version 0.16.0. Added `electron/mdns.ts`, `electron/mdns.test.ts`, `electron/networkDiscovery.test.ts`. Modified `electron/networkDiscovery.ts`, `electron/main.ts`, `electron/preload.ts`, `src/App.tsx`, `src/style.css`, `src/vite-env.d.ts`, `CONTEXT.md`, this log. No new dependency: the mDNS resolver is about 140 lines of `node:dgram`.
